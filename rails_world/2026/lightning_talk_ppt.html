⏱️ (0:20 - 1:00) The Problem Statement

We were told: skinny models, fat services. Single Responsibility. One class, one reason to change. We Rubocop'd our souls clean.

And somewhere in that religion, we forgot one key reality: the database does not care about your object graph.

PostgreSQL has spent 30 years becoming an absolute genius at set operations.

And we hired this engine—then handed it work one row at a time, through five layers of PORO abstractions.

The "Clean" Crime Scene


# SOLID, code-review-approved, architecture-monk approved
class OrderTotalCalculator
  def initialize(order) = @order = order
  def call = @order.line_items.sum { |li| LineItemPricer.new(li).price }
end

class LineItemPricer
  def initialize(li) = @li = li
  def price = @li.quantity * @li.product.current_price
end

# In a controller, looking completely innocent:
orders.map { |o| OrderTotalCalculator.new(o).call }

N+1 query explosion across 3 object boundaries.
Bullet can't warn you; .includes() has nowhere to attach.

⏱️ (1:00 - 2:15) Code Breakdown

This code easily passes code review. Every object has a single job. It's clean, SOLID-approved architecture.

[Click to highlight line 13]: But in production? It fires—count with me—a query for line items, then a query per line item for products.

On just 200 orders, that is over 400 SQL round trips.

Each query is wrapped so deeply in POROs that the Bullet gem can't even warn you, and .includes() has nowhere to attach.

We didn't eliminate the N+1 query... we gave it a service object and a permanent address!

The "Dirty" Solution


class Order < ApplicationRecord
  scope :with_totals, -> {
    joins(line_items: :product)
      .group(:id)
      .select("orders.*, SUM(line_items.quantity * products.current_price) AS total")
  }
end

# Usage:
Order.with_totals # 1 Query. 0 Ruby allocations.

Service Objects (Ruby PORO Loop)

3,200 ms

Active Record Scope (Postgres C Engine)

12 ms

⏱️ (2:15 - 3:30) The Active Record Solution

Here is the fix: Exactly 1 query. The set math happens directly inside PostgreSQL in compiled C code, on data that never leaves database memory.

[Click to next highlight]:

Look at those benchmark numbers: 3,200 milliseconds down to 12 milliseconds.

Yes—the logic lives on the model. Yes—it's raw SQL inside a scope. Your team's architecture monk might object.

But it runs 250 times faster, and the query intent is unified in a single place.

This "dirty" version isn't dirty at all—it's just honest about where execution happens.

Abstraction moved work to the wrong machine.

The Abstraction Wall

Every abstraction boundary in Ruby is a wall the query planner can't see through.

Break queries into isolated POROs and you amputate includes, CTEs, and window functions.

Where Optimization Belongs

Clean architecture optimized for the reader of the class.

It pessimized the machine running the query. Someone always pays at 2 AM.

⏱️ (3:30 - 4:30) Core Takeaway & Paradigm Shift

Here is the real flaw in "clean" query code: every abstraction is a Ruby wall that the query planner cannot see through.

PostgreSQL superpowers like includes, eager_load, CTEs, and window functions only work when the query remains whole.

Splitting logic across six tiny objects depletes the capabilities you bought PostgreSQL for in the first place.

Clean architecture optimized for the reader of the code, but heavily defeats the machine executing the work. Someone always pays for that—usually production, at 2 AM.

The 3 Commandments

RULE 01

Fat Model, Rich Scopes

Keep query logic where PostgreSQL can see the entire execution graph.

✓ Composite Scopes
✓ Chainable SQL Relations
RULE 02

Push Work to Postgres

Let C do set math. Stop pulling thousands of rows into Ruby memory.

⚡ CTEs & Window Functions
⚡ Scenic Materialized Views
RULE 03

Side-Effects Only

Limit Service Objects to external orchestration—never as SQL wrappers.

✓ Stripe / Emails / BG Jobs
🛑 NO find or sum wrappers

⏱️ (4:30 - 5:20) Practical Rules

I am not anti-abstraction. I am anti-abstracting the one engine your application relies on most.

Rule 1: Keep query logic in models so PostgreSQL sees the full execution graph.

Rule 2: Let C handle set operations—stop fetching thousands of Active Record instances into Ruby memory just to run .select or .map.

Rule 3: Reserve Service Objects strictly for side effects—Stripe payments, sending emails, external API calls. They are not a witness protection program for SQL queries!
